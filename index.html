ArgoCD Integration — Shopify Setup on AKS

Subscription: ShopLC-DEV-Shopify-Apps Env: DEV Location: US Author: Pururaj Choudhary Date: 24 Jun 2026

A comprehensive guide to setting up Argo CD on the AKS environment — from cluster ingress to exposing the UI through Application Gateway, wiring up GitHub, and enabling self-heal.

Goals
  • Set up and integrate Argo CD on the AKS cluster
  • Expose the Argo CD UI using the Application Gateway
  • Set up the GitHub repos with Argo CD
  • Enable self-heal and automatic deployment in Argo CD
Infrastructure requirements
  • AKS cluster
  • SH VM
  • Helm installed on SH VM & AKS
  • GitHub repo
  • Application Gateway
  • DNS name
Steps to set up Argo CD
  1. Set up the ingress file for Argo CD — create and edit argocd-ingress.yaml:
    vim argocd-ingress.yaml
    apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: argocd-ingress
  namespace: argocd
  annotations:
    appgw.ingress.kubernetes.io/appgw-ssl-certificate: ssl-tjc.tv
    appgw.ingress.kubernetes.io/use-private-ip: "true"
spec:
  ingressClassName: azure-application-gateway
  rules:
  - host: argocddevtvp.tjc.tv  # change host to required name
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: argocd-server
            port:
              number: 80
  2. Create the namespace 
    kubectl create namespace argocd
  3. Add the Argo Helm repo 
    helm repo add argo https://argoproj.github.io/argo-helm
  4. Update Helm repos 
    helm repo update
  5. Install Argo CD 
    helm install argocd argo/argo-cd \
  --namespace argocd
  6. Retrieve the initial admin password 
    kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d
  7. Edit values.yaml and add: 
    configs:
  params:
    server.insecure: true
  8. Upgrade the release with the updated values 
    helm upgrade argocd argo/argo-cd -n argocd -f values.yaml
  9. Apply the ingress 
    kubectl apply -f argocd-ingress.yaml -n argocd
Steps to add multiple clusters to a single Argo CD
  1. Network requirement — clusters must be on the same network.
  2. Install the Argo CD CLI on the SH VM: 
    curl -sSL -o argocd https://github.com/argoproj/argo-cd/releases/latest/download/argocd-linux-amd64
chmod +x argocd
sudo mv argocd /usr/local/bin/
  3. Log in via the CLI 
    argocd login <argocdshopifydev.tjc.tv>
    ⚠ Use the configured domain, with the admin user and its password.
  4. Get the target cluster's context 
    kubectl config get-contexts
  5. Register the new cluster 
    argocd cluster add <cluster-name>
    ✓ Verify in the UI under Settings → Clusters — the new cluster should be listed there.

Argo CD — Create a Read-Only User (SSO Configuration)

Namespace: argocd IdP: Azure AD (OIDC) Server: argocdshopifydev.tjc.tv

Adds a dedicated read-only account to Argo CD, wires the instance up to Azure AD via OIDC for SSO, and scopes access with RBAC so the account (and any SSO group) can only view — never modify.

Step 1 — Inspect current config
kubectl get ns
kubectl get cm argocd-cm      -n argocd -o yaml
kubectl get cm argocd-rbac-cm -n argocd -o yaml
Step 2 — Declare the account & configure OIDC

Under argocd-cm's data:, declare the account: 

accounts.readonly: login

Create the OIDC client secret:

create client secret
kubectl -n argocd patch secret argocd-secret \
  -p '{"stringData": {"oidc.azure.clientSecret": "<your-client-secret-value>"}}'

Then edit the ConfigMap:

kubectl edit cm argocd-cm -n argocd
apiVersion: v1
data:
  admin.enabled: "true"
  url: https://argocdshopifydev.tjc.tv
  application.instanceLabelKey: argocd.argoproj.io/instance
  application.sync.impersonation.enabled: "false"
  exec.enabled: "false"
  oidc.config: |
    name: Azure
    issuer: https://login.microsoftonline.com/448203bd-eb06-47eb-916c-af6b29c0dcb8/v2.0
    clientID: d5ff4bff-bd3f-4e0a-98c0-306dc22f4596
    clientSecret: $oidc.azure.clientSecret
    requestedIDTokenClaims:
      groups:
        essential: true
    requestedScopes:
     - openid
     - profile
     - email
Step 3 — Grant RBAC access

Under argocd-rbac-cm's data.policy.csv, add: 

g, readonly, role:readonly

Full example after editing:

kubectl edit cm argocd-rbac-cm -n argocd
apiVersion: v1
data:
  policy.csv: |
    p, role:sync-only, applications, get, */*, allow
    p, role:sync-only, applications, sync, */*, allow
    g, <sync-group-object-id>, role:sync-only
    g, <admins-group-object-id>, role:admin
    g, <readers-group-object-id>, role:readonly
  policy.default: ""
  policy.matchMode: glob
  scopes: '[groups]'
kind: ConfigMap
metadata:
  annotations:
    meta.helm.sh/release-name: argocd
    meta.helm.sh/release-namespace: argocd
  labels:
    app.kubernetes.io/component: server
    app.kubernetes.io/instance: argocd
    app.kubernetes.io/managed-by: Helm
    app.kubernetes.io/name: argocd-rbac-cm
    app.kubernetes.io/part-of: argocd
    app.kubernetes.io/version: v3.4.4
    helm.sh/chart: argo-cd-9.7.0
  name: argocd-rbac-cm
  namespace: argocd

Useful checks while wiring RBAC up:

current rbac & user info
# current RBAC
kubectl -n argocd get cm argocd-rbac-cm -o jsonpath='{.data.policy\.csv}'

# find User Info, an alternative check
kubectl -n argocd logs deploy/argocd-server | grep -i -E "rbac|claim|group" | tail -30
Step 4 — Restart the server (if changes don't auto-apply)
kubectl rollout restart deployment argocd-server -n argocd
kubectl rollout status  deployment argocd-server -n argocd
Step 5 — Verify the account exists

Expect to see both admin and readonly listed:

argocd account list
Step 6 — Log in as admin, set the new user's password
argocd login <ARGOCD_SERVER>
argocd account update-password \
  --account readonly \
  --new-password '<strong-password>'
Step 7 — Confirm as the read-only user
argocd login <ARGOCD_SERVER> \
  --username readonly \
  --password '<strong-password>'
✓ A successful login with no write access confirms the read-only account and SSO/RBAC wiring are working as expected.

KEDA — Kubernetes Event-Driven Autoscaling

Namespace: custom Event source: Azure Event Hub API: keda.sh/v1alpha1

Currently we use Azure Event Hub as a Kafka alternative. There are two ways to implement KEDA against it, depending on how the consuming application talks to Event Hub.

How it works
  • Event Hub can operate in two modes: as a Kafka endpoint, or as a native Event Hub endpoint.
  • If the application uses a Kafka SDK, Event Hub behaves like Kafka and stores consumer lag itself — KEDA's kafka trigger scales directly off that.
  • If the application uses the Azure Event Hub SDK, Event Hub requires a storage account to persist the consumer lag/checkpoint, and KEDA's azure-eventhub trigger reads from there instead.
ℹ The configuration below covers the Kafka-endpoint path — used when the application connects via a Kafka SDK.
TriggerAuthentication

References the Kafka-mode secret for SASL credentials:

trigger-auth.yaml
apiVersion: keda.sh/v1alpha1
kind: TriggerAuthentication
metadata:
  name: customerconsumer-kafka-trigger-auth
  namespace: custom
spec:
  secretTargetRef:
    - parameter: username
      name: kafka-eh-secret-kafka
      key: username
    - parameter: password
      name: kafka-eh-secret-kafka
      key: password
ScaledObject

Scales the deployment on the Kafka lag trigger, with a memory trigger as a secondary safeguard:

scaledobject.yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: customerconsumer-api-scaledobject
  namespace: custom
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: customerconsumer-api
  minReplicaCount: 1
  maxReplicaCount: 2
  pollingInterval: 15
  cooldownPeriod: 60
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleUp:
          stabilizationWindowSeconds: 30
          policies:
            - type: Pods
              value: 2
              periodSeconds: 30
        scaleDown:
          stabilizationWindowSeconds: 120
          policies:
            - type: Pods
              value: 1
              periodSeconds: 60

  triggers:
    - type: kafka
      metadata:
        bootstrapServers: SLC-Prod-Shopify-App-EH.servicebus.windows.net:9093
        consumerGroup: customer-inactive-push-consumer-group
        topic: ca.customer.inactive-push
        lagThreshold: "5000"
        activationLagThreshold: "2000"
        sasl: plaintext
        tls: enable
      authenticationRef:
        name: customerconsumer-kafka-trigger-auth

    - type: memory
      metricType: Utilization
      metadata:
        value: "70"
⚠ lagThreshold is the target lag per replica; activationLagThreshold is the minimum lag before KEDA activates a scale-from-zero-or-idle event.
Kubernetes secret

Holds the Kafka-mode SASL credentials referenced by the TriggerAuthentication above:

kafka-eh-secret.yaml
apiVersion: v1
kind: Secret
metadata:
  name: kafka-eh-secret
  namespace: custom
type: Opaque
stringData:
  sasl: "plaintext"
  tls: "enable"
  username: "$ConnectionString"
  password: "endpoint connection string"

ELK Stack Setup on a VM

Stack: Elasticsearch + Kibana + Nginx Repo: Elastic 9.x apt OS: Debian/Ubuntu

A single script that adds the official Elastic apt repository, installs Elasticsearch, Kibana, and Nginx, and pre-wires Nginx as a reverse proxy in front of Kibana. Services are installed but deliberately not started — that's a separate step once config is reviewed.

What it does
  • Adds the Elastic GPG key and the 9.x apt repository
  • Installs Elasticsearch, Kibana, and Nginx via apt
  • Writes an Nginx reverse-proxy config pointing at Kibana on localhost:5601
  • Enables the site, removes the default Nginx site, and validates the config with nginx -t
Setup script
elk-setup.sh
#!/bin/bash
# Add Elastic GPG Key
wget -qO - https://artifacts.elastic.co/GPG-KEY-elasticsearch | \
sudo gpg --dearmor -o /usr/share/keyrings/elasticsearch-keyring.gpg

# Install required package
sudo apt-get install -y apt-transport-https

# Add Elastic repository
echo "deb [signed-by=/usr/share/keyrings/elasticsearch-keyring.gpg] \
https://artifacts.elastic.co/packages/9.x/apt stable main" | \
sudo tee /etc/apt/sources.list.d/elastic-9.x.list

# Update package list
sudo apt-get update

# Install Elasticsearch, Kibana, and Nginx
sudo apt-get install -y elasticsearch kibana nginx

# Create Nginx config for Kibana reverse proxy
sudo tee /etc/nginx/sites-available/kibana > /dev/null <<EOF
server {
    listen 80;
    server_name your_domain_or_ip;
    location / {
        proxy_pass http://localhost:5601;
        proxy_http_version 1.1;
        proxy_set_header Upgrade \$http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host \$host;
        proxy_cache_bypass \$http_upgrade;
    }
}
EOF

# Enable Nginx site
sudo ln -sf /etc/nginx/sites-available/kibana /etc/nginx/sites-enabled/kibana

# Optional: remove default site
sudo rm -f /etc/nginx/sites-enabled/default

# Test Nginx config (won't start it)
sudo nginx -t

echo "Installation complete. Services are NOT started."
ℹ Before going further, edit server_name in the Nginx config to your actual domain or IP, then start the services when ready: sudo systemctl start elasticsearch kibana nginx.

KEDA Kafka Trigger Misconfiguration

13 Event Hub consumer services silently mis-scaled from a Kafka-vs-Event-Hub trigger type mismatch.

Incident · High
Issues & Solutions  /  Incident Report

KEDA Kafka Trigger Misconfiguration

Severity: High Status: Resolved Services affected: 13 Namespace: decustomsvc Date: 26 Jun 2026
Issue

13 Kafka consumer microservices in AKS had their KEDA ScaledObject triggers set to azure-eventhub, even though the applications were built with KafkaJS. This caused auto-scaling to fail and behave unpredictably across all affected services.

Cause

KafkaJS stores consumer offsets in the Kafka broker's __consumer_offsets topic, but the azure-eventhub trigger type looks for checkpoints in Azure Blob Storage instead. That mismatch meant KEDA was checking a location the application never wrote to, so it could never calculate real message lag.

Impact
  • ScaledObjects stuck in ScaledObjectCheckFailed / UnknownState
  • HPA metrics unavailable — memory: <unknown>/70%
  • Pods scaling erratically, with no correlation to actual message load
  • Continuous KEDA operator warnings every 30 seconds
  • Elevated risk of service degradation during high-traffic periods, across all 13 services
Resolution

Changed the trigger type from azure-eventhub to kafka on every affected ScaledObject, and updated the paired TriggerAuthentication to use SASL username/password instead of the Azure SDK's connection/storageConnection parameters.

the fix
- type: azure-eventhub  # ❌ wrong — expects Blob Storage checkpoints
+ type: kafka           # ✅ correct — reads offsets from Kafka broker
✓ Verified via kubectl logs -n keda deployment/keda-operator and ScaledObject status returning READY=True with lag metrics flowing normally.
